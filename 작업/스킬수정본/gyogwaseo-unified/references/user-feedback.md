# 사용자 눈검수 이후의 수정·2차 검수

**제작 → 기존 독립 검수 → 사용자 직접 눈검수 → 제작팀 수정 → 2차 독립 검수**를 연결한다. 이후 차수에도 반복한다. S·L·M·N·J·K·R과 문항 2인 블라인드 풀이는 유지하며, 사용자 지적은 추가 검수 기준이다.

## 접수와 기록

1. 실제 검수한 DOCX를 전달하고 `1차 제작·검수 완료 / 사용자 검토 대기`로 구분한다. PDF는 내부 검수용으로 보존하며 기본 전달하지 않는다. ‘최종 출고’ 요청일 때는 [전체통합본+분권 5개](split-delivery.md)의 DOCX 6개 기준을 적용한다. 사용자 승인이나 가상의 추가 요청을 만들지 않는다.
2. 요청을 받으면 **수정 전에**, 출고 기록 JSON과 같은 폴더의 `사용자수정요청.json`에 누적 기록하고 출고 기록의 `user_feedback.ledger`를 연결한다. 검수 전에는 `review` 참조를 생략한 대기 상태로 둔다. 교재가 아직 바뀌지 않았어도 새 요청은 미완료다.
3. 요청마다 안정된 ID(예: UR-001), **사용자 원문**, 실제 메시지·이미지 근거, 대상 위치, 확인할 세부 조건을 기록한다. 제작자의 해석·제안은 사용자 원문과 구별한다. 한 메시지의 여러 요청을 빠뜨리지 않도록 나눈다. ‘나머지도 전부’이면 같은 유형 전체를 대상에 넣고, 쪽 번호와 함께 문장/문항 ID나 인용도 적는다.
4. 기존 요청은 삭제하지 않는다. 철회·대체는 사용자의 실제 결정과 대체 ID를 남긴다. 새 요청은 추가하고 `round_id`를 갱신한다. 원장 변경 전에는 이전 원장과 확인서를 차수별 보관한다.
5. 명확한 최신 사용자 지시가 이전 기준보다 우선한다. 뜻·범위가 모호하거나 양립할 수 없는 경우만 예·추천안을 하나씩 제시하고 답을 기다린다. 해당 교재 요청을 다른 교재·공통 스킬 규칙으로 임의 승격하지 않는다. 공통 규칙 수정까지 요청받았다면 그 범위도 기록한다.

원장의 사실을 기존 `수정이력.txt`에 같은 ID로 연결하고, `수정인계.txt`에는 현재 유효 요청·미완료 상태·원장 위치만 둔다. 서로 다른 요청 원본 두 벌을 유지하지 않는다. 다른 팀/새 채팅에서도 원장과 사용자 근거를 먼저 읽는다.

## 제작팀 수정과 2차 독립 검수

- 제작팀은 변경 전후·위치·연동 수정·담당자/실행을 기록한다. `applied`는 반영 상태이며 검수 통과가 아니다. 이미 충족하면 억지로 수정하지 않고 `no_change_needed`와 현재 근거를 기록한다.
- 검수팀은 현재 원장, 이전/현재 버전, 필요한 원문·원고/FINAL·실제 DOCX/PDF와 기존 지침을 받고 **기존 기준 + 모든 현재 유효 요청의 세부 조건**을 실제 파일에서 확인한다. 한 예시 수정으로 전체 유사 유형 확인을 대신하지 않는다.
- 영향받는 L·M/N·J/K·R을 기존 절차대로 실행한다. 기록만 추가됐다는 이유로 모든 검수를 반복하지 않지만, 연동 각주·해석·문항·정답·쪽 흐름은 빠뜨리지 않는다. 영향이 불명확하면 해당 단계의 범위를 넓힌다.
- **사용자 원장과 전후 대조는 정답을 드러낼 수 있으므로 questions-blind에 첨부하지 않는다.** M/N의 현재 학생용 문항 풀이와 답·근거 저장 후 questions-compare에서 요청·정답·해설을 확인한다. 이미 답을 본 검수자를 새 블라인드 검수자로 세지 않는다.
- 변경 0건·이미 충족도 실제로 확인한다. `--changed-only` 결과가 비었다고 요청 검수를 생략하지 않는다. 실패·미확인·결정 대기는 제작팀에 되돌리고 수정 뒤 바뀐 버전을 재확인한다.
- 요청 확인서는 기존 2차 검수자가 실제 결과에서 작성한다. 새 검수 종류나 추가 인원을 반드시 만드는 규칙이 아니다. 제작자의 자기확인이나 가짜 검수자·실행 ID로 대신하지 않는다.

## 원장·확인서 형식

작업 기록은 학생용 교재와 스킬 패키지 밖에 둔다. 원장 최상위는 `schema_version:1`, 실제 차수 `round_id`, 누적 배열 `requests`다.

| 요청 항목 필드 | 내용 |
|---|---|
| id | 중복 없는 안정된 요청 ID |
| user_text, source | 사용자 원문과 날짜/메시지/보존 이미지 등 실제 근거 위치 |
| targets | 대상 ID·인용·역할·쪽·적용 범위를 적은 비어 있지 않은 문자열 배열 |
| criteria | 각각 확인할 조건의 비어 있지 않은 문자열 배열 |
| disposition | active / withdrawn / superseded |
| implementation | status, 실제 producer_id, execution_id, 변경 전후·위치·근거를 적은 detail |
| decision | 철회·대체 시 실제 사용자 결정의 user_text와 source 필수 |
| superseded_by | 대체 시 목록 안의 실제 후속 요청 ID. 자기참조·순환 금지 |

반영 status는 pending / applied / no_change_needed / blocked 중 실제 상태다. 미반영·미확인을 숨기려고 요청을 철회·대체하지 않는다.

별도 `사용자요청_2차검수.json`(후속 차수는 실제 차수로 구별)에 검수자가 기록한다.

| 확인서 필드 | 내용 |
|---|---|
| schema_version, round_id | 정수 1과 현재 원장의 차수 |
| ledger_sha256 | 실제 확인한 원장 파일 바이트 SHA-256 |
| bindings | 현재 package_sha256 및 manuscript/plan/contract/docx/pdf/learning_final/assessment_final 각각의 _sha256 파일 지문 |
| reviewer_id, execution_id, performed_at | 실제 독립 검수자·실행·시각 |
| independent, status | 실제 독립 여부와 결과. 수행 전 PASS를 채우지 않음 |
| checks | 모든 active 요청마다 정확히 하나의 {request_id,status,results:[...]} |
| results | 각 criteria마다 {criterion_index:0부터시작,status,evidence}. 현재 위치·관찰 결과를 evidence에 기록 |

출고 기록에는 다음처럼 연결한다. 아래는 형식 설명이며 실제 완료 증거가 아니다.

```json
"user_feedback": {
  "ledger": {"path": "사용자수정요청.json", "sha256": "ACTUAL_LEDGER_SHA256"},
  "review": {"path": "사용자요청_2차검수.json", "sha256": "ACTUAL_REVIEW_SHA256"}
}
```

`verify_release.py`가 `user_feedback.py`로 요청·조건 누락/중복, 제작자와 검수자 분리, 현재 원장·확인서·산출물 연결을 검사한다. 출고 기록 폴더에 `사용자수정요청.json`이 있으면 연결을 빠뜨리거나 보관된 옛 원장을 대신 연결할 수 없다. 새 요청이나 반영 변경으로 원장이 바뀌면 옛 확인서는 유효하지 않다. 기존 검수·출고 게이트도 그대로 필요하다.

기계는 기록의 연결을 검사하며 실제 의미·반영 품질을 증명하지 않는다. 채팅에만 있고 기록하지 않은 요청은 알 수 없으므로 **제작팀의 접수 즉시 기록과 검수팀의 사용자 근거 대조**가 필수다.

## 상태와 전달

`1차 제작·검수 완료 / 사용자 검토 대기` → `추가 요청 접수 / 수정 중` → `추가 요청 반영 / 2차 검수 대기` → 모든 active 조건을 실제 확인했을 때 `추가 요청 반영·2차 검수 완료`로 구분한다.

완료 보고에는 요청 수·반영/이미 충족/미완료·검수 결과, 최신 DOCX와 기록 위치를 제공한다. PDF는 내부 검수에 사용하고 기본 전달하지 않는다. 최종 출고는 현재 전체통합본과 분권 5개의 실제 DOCX 및 그 여섯 파일을 담은 전달 ZIP을 함께 검증하고 ZIP 링크를 제공한다. 응답 부재를 사용자 승인으로 표시하지 않는다. 후속 요청이 오면 상태를 다시 열고 반복한다. 원장이 없는 기존/최초 작업의 `NOT_RECORDED`는 사용자 승인이나 ‘추가 요청 없음’의 증거가 아니다.
